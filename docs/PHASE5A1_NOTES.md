## 最小資料方案：不改 Schema

| 資訊 | 保存／取得方式 | 不會採用的替代方式 |
|---|---|---|
| `selected_total_notes` | Session 原始選歌 `ocr_fields.total_notes`；舊 Session 使用原始 `fields` | 不以 CSV 或判定合計冒充選歌 OCR |
| `database_total_notes` | 明確 Song ID + EASY/NORMAL/HARD 的既有 GameDifficulty | 不按同名取第一首 |
| `judged_total` | 審核表單的有效 P+C+B+M；另列 `ocr_judged_total` 保存原始辨識合計 | NULL 不補 0；不回填完整數 |
| `verified_total_notes` | 已確認身份下，與既有已驗證資料一致，或明確人工確認的完整數 | 來源驗證不等於已驗證差異規則 |

上述核對結果包含來源、信心度、Difficulty ID、差異、待確認原因。使用者保存草稿時寫在審核側錄 JSON 的 `note_sources`；正式提交時連同原始 OCR／Session 保存到既有 `PlayRecord.evidence_json`。正式資料表的 `total_notes` 仍表示經驗證的完整數。原始 OCR、原始 Session 和圖片不被審核值覆蓋。

沒有新增 SQLite 欄位的必要，因此不執行 migration。若未來需要對音符來源做跨紀錄 SQL 分析，再提案增加可索引的欄位；本次不提前加入。未來例外規則必須獨立保存差異、理由、證據、確認人／方式與適用範圍，並另行設計資料庫限制；本版不提供勾選即放行的功能。歌曲尚待最後人工確認時，也會先顯示已選候選的歌曲庫音符差異與條件式算式；verified_total_notes 仍保持 NULL，正式 MAX／燈號不會因此成立。

## 自動填入與身份安全

### 官方 K

即時監控使用明確設定的 Official 來源；待確認頁沒有來源證據時，需由使用者勾選「已確認本次是官方 K 模式」。這和搜尋篩選是兩個不同用途，切換搜尋分類不構成來源確認。

核對可靠的歌名、EASY/NORMAL/HARD、歌曲 LV，並檢查所有已提供的音符數／BPM。一個必要欄位缺失、低信心、觀測衝突、同名候選資料未知或最後仍有多個符合候選，都不自動選 Song ID。只有唯一可靠 K 身份時，才帶入相應 Song／GameDifficulty，空白的 LV／音符數可從已驗證資料補上。fileId、Artist、BPM 顯示於核對資訊。

官方資料不再受 Custom 必須確認 Pack 與遊戲時間的條件阻塞；官方歌曲不具有實體 Pack／SongFolder。Custom 的完整匹配條件維持嚴格。

新 Session 同時保存原始 `ocr_fields` 與補充後的 `fields`。從歌曲庫填入的資料標記 `official_catalog_fill`，不冒充 OCR 值。即使官方身份可靠，正式提交仍需要使用者核對本人與歌曲身份，不自動勾選這些確認。

### Custom／connect

維持 Pack、歌名、E/N/H、LV、完整數、遊戲時間的完整比對，以及 Song ID、Root、SongFolder 的穩定身份。已有完整人工確認的 Review 或既有 ManualReferences 可供重用；讀取舊確認只產生記憶體內對應，不改寫原檔。

重用前檢查原圖 SHA-256、Session 內容、歌曲路徑與已保存確認的一致性。未確認／缺時間／音符有差異的草稿不能建立可信對應；原圖被改、資料庫路徑不同、已驗證資料衝突也不能重用。同名未知候選不能被一筆舊對應排除，無 Pack 的多人 Session 仍須人工選擇。connect 與其他 Pack 保持各自身份。待確認頁每次核對時讀取最新對應；即時監控在啟動時載入歌曲庫與可信對應，新保存的對應於下一次開始監控時生效，本版不宣稱已支援監控中的熱更新。

## 實際操作

1. 重新啟動 `MonitorGUI.cmd`，開啟「待確認成績」。本次已啟動的新頁面為 <http://127.0.0.1:40470/reviews>；服務關閉後可重新由啟動檔開啟。
2. 具備可靠鎖定來源的未審核紀錄可自動填入提案；既有人工草稿不自動改寫。已明確選定 Song ID 後，選擇難度可填入該難度已驗證的空白數值。
3. Heart of Witch 這筆缺少原選歌資訊：選 **HARD**、確認 **官方 K**，按「核對來源並填入已知資料」。系統帶入 **4343／1194**；LV29 與 P1145/C30/B7/M10 保持原值。不從 LV 猜 HARD，也不從歌名猜 Official。
4. 看「音符數來源核對」，檢查選歌、歌曲庫、原始 OCR 與目前修正的合計。完整數與判定有差異時可按「保存草稿」，重啟可繼續處理。
5. 「確認資料（另存）」和「確認並儲存成績」在未釐清差異時停用。條件式 MAX 不表示已正式確認；不改數字來繞過驗證。

自動填入只修改目前表單的空白欄位；已有值出現衝突時列出問題並停止填入。API 提案不保存草稿、不更改人工確認旗標、不寫 PlayRecord。使用者明確保存時才持久化。

## 驗證與限制

完整 **226 項測試通過**（原 199 + 新 27），沒有跳過。涵蓋 Heart 差異與條件式計分、四種音符來源、NULL、GAME OVER、低信心、官方唯一／多候選、同名跨來源、舊確認重用及原圖變更、官方空白資料填入、HTTP 權限與唯讀提案。既有計分、多人第二列、冪等提交、備份／交易回滾、重啟查詢、Phase1–4C 回歸持續通過。

本次新執行 3 張原始截圖的 OCR：Heart of Witch、Cagayake 與多人結算，單張約 0.5～1.1 秒（各次精確耗時見報告 JSON）。這是單次本機 CPU OCR，包含不同畫面與 ROI 工作量，不是即時效能基準；未新增 CPU／記憶體測量。

正式庫完整副本中，Heart 差異草稿可保存與重新載入，但確認及提交均失敗；Cagayake 一致成績可正式提交為 MAX -3／AC，重送返回同一筆 Record。GUI 實際操作驗證來源核對、填入1194、草稿保存與重載、條件式預覽及停用的正式提交按鈕。

Windows HTTP 拒絕請求時，會先限量丟棄未讀的小型 POST 內容，再回傳原有 403／錯誤訊息，避免 TCP 提前 reset；不解析或授權被拒絕的內容。針對權限拒絕與唯讀提案另有實際 HTTP 測試。
